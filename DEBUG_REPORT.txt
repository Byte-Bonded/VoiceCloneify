[C-01] BROKEN QUERY EXPANSION IN ATTENTION POOLING
File:    streamvc/model.py — LearnableAttentionPooling.forward()
Lines:   ~130–150

Problem:
  self.query = nn.Parameter(torch.randn(1, output_dim))
  ...
  query = self.query.expand(B, -1, -1)  # Attempting to expand 2D → 3D

  PyTorch's expand() can prepend new singleton dimensions, so the result is
  shape (B, 1, output_dim). While technically it can work in some PyTorch
  versions, this relies on undocumented behavior that "new dimensions are
  appended at the front." The safe, explicit, and canonical form is to call
  unsqueeze(0) first. The current form can silently produce wrong batch
  shapes in PyTorch builds that don't support this extension.

Fix:
  # Change parameter init to include the batch-singleton dimension:
  self.query = nn.Parameter(torch.randn(1, 1, output_dim))
  ...
  # In forward():
  query = self.query.expand(B, -1, -1)  # Now (B, 1, output_dim) — unambiguous

[C-02] CONTENT PROJECTION LAYER NOT SAVED OR LOADED IN CHECKPOINTS
File:    streamvc/train.py — save_checkpoint() / load_checkpoint()
Lines:   ~355–405

Problem:
  self.content_projection = nn.Linear(content_dim, hubert_dim).to(self.device)

  This layer is added to optimizer_g and trained throughout the run.
  However, save_checkpoint() only serializes:
    {'model': ..., 'discriminator': ..., 'optimizer_g': ..., 'optimizer_d': ...}

  content_projection is completely absent. When training is resumed, the
  projection layer is re-initialized from scratch with random weights,
  invalidating all previously learned centroids projection. HuBERT pseudo-labels
  become meaningless after resume, silently corrupting content loss.

  torch.save({
      ...
      'content_projection': self.content_projection.state_dict(),
      ...
  }, checkpoint_path)

  # In load_checkpoint():
  self.content_projection.load_state_dict(checkpoint['content_projection'])

[C-03] NON-CAUSAL DOWNSAMPLING IN CONTENT ENCODER BREAKS STREAMING GUARANTEE
File:    streamvc/model.py — ContentEncoder.__init__()
Line:    ~90

Problem:
  self.downsample = nn.Conv1d(
      hidden_dim, hidden_dim,
      kernel_size=self.hop_length * 2,   # 640
      stride=self.hop_length,            # 320
      padding=self.hop_length // 2       # 160 samples = 10ms look-ahead
  )

  The padding of 160 samples introduces a 10ms future look-ahead into the
  CONTENT ENCODER. The entire architecture is designed to be causal/streaming
  (60ms latency claim), but this single non-causal layer invalidates the
  streaming constraint. All paper claims about latency are broken at inference.

Fix:
  Use asymmetric (causal) padding: pad only the left (past) side, none
  on the right (future):

  # Option A — Manual causal padding:
  self.downsample = nn.Conv1d(
      hidden_dim, hidden_dim,
      kernel_size=self.hop_length * 2,
      stride=self.hop_length,
      padding=0  # No automatic padding
  )
  # In forward, before downsample:
  # x = F.pad(x, (self.hop_length * 2 - 1, 0))  # Left-only padding

  # Option B — Wrap with CausalConv1d logic applied to strided conv.

[C-04] TRIPLE FORWARD PASS PER TRAINING STEP — MEMORY EXPLOSION
File:    streamvc/train.py — train_step()
Lines:   ~175–260

Problem:
  A single train_step() runs THREE full model forward passes:

  Pass 1 (gradient):
    output_audio, content_logits = self.model(source_audio, target_mel, f0_features)

  Pass 2 (no_grad, to compute hubert targets):
    _, content_features = self.model.content_encoder(source_audio)
    hubert_targets = self.compute_hubert_targets(content_features)

  Pass 3 (no_grad, for discriminator training):
    output_audio_det, _ = self.model(source_audio, target_mel, f0_features)

  Pass 1 already computes content_logits from content_encoder. Pass 2
  re-runs content_encoder independently (wasteful). Pass 3 re-runs the
  entire model (very wasteful). This triples memory bandwidth and
  computation per step, explaining extremely slow VRAM usage.

Fix:
  # Detach output from Pass 1 for discriminator training:
  output_audio_det = output_audio.detach()

  # Cache content_features from Pass 1 by modifying model.forward()
  # to return them, or expose content encoder call externally.
  # Then compute hubert_targets from the already-available content_features.

  # Eliminate all redundant forward passes.

[M-01] SAME-SPEAKER PAIRS ALLOWED IN DATASET — COLLAPSES VOICE CONVERSION TRAINING
File:    streamvc/dataset.py — __getitem__()
Lines:   ~100–115

Problem:
  target_idx = random.randint(0, len(self.audio_files) - 1)
  # target_idx can equal idx — same file, same speaker

  Voice conversion training requires source and target to be DIFFERENT
  speakers so the model learns to disentangle speaker identity from content.
  When source == target, the trivial optimal solution is identity mapping:
  the model learns to copy audio rather than convert speakers. With 33,236
  files, P(same file) = 1/33236 ≈ 0.003%, but with clustered datasets like
  LibriTTS where many files share a speaker, same-SPEAKER pairs are far more
  frequent. This silently degrades speaker disentanglement.

Fix:
  # Build a speaker-indexed lookup at init:
  self.speaker_files = {}  # {speaker_id: [file_paths]}
  for f in self.audio_files:
      spk = f.parts[-3]  # LibriTTS: root/speaker_id/chapter/file
      self.speaker_files.setdefault(spk, []).append(f)
  self.speakers = list(self.speaker_files.keys())

  # In __getitem__, pick a different speaker:
  source_speaker = source_path.parts[-3]
  target_speaker = random.choice(
      [s for s in self.speakers if s != source_speaker]
  )
  target_path = random.choice(self.speaker_files[target_speaker])

[M-04] DISCRIMINATOR LOSS MISMATCH — HINGE LOSS FOR REAL, MSE FOR FAKE
File:    streamvc/discriminator.py — discriminator_loss() / generator_adversarial_loss()
Lines:   ~167–210

Problem:
  The discriminator uses hinge loss:
    loss_real = torch.mean(F.relu(1.0 - dr))
    loss_fake = torch.mean(F.relu(1.0 + df))

  But generator_adversarial_loss uses MSE (LSGAN):
    loss += torch.mean((1.0 - df) ** 2)

  These are two incompatible GAN formulations (Hinge-GAN vs. LSGAN).
  Using Hinge discriminator with LSGAN generator is theoretically inconsistent
  and produces suboptimal gradient signals. Either use Hinge throughout or
  LSGAN throughout.

Fix (Hinge throughout — consistent with paper):
  def generator_adversarial_loss(disc_fake_outputs):
      loss = 0.0
      for df in disc_fake_outputs:
          loss -= torch.mean(df)   # Hinge generator loss
      return loss / len(disc_fake_outputs)

[M-05] F0 FEATURES INCONSISTENCY — WHITENED F0 vs. RAW LOG-F0 IN SAME VECTOR
File:    streamvc/f0_extractor.py — compute_uncertainty_features()
Lines:   ~105–130

Problem:
  # Feature 0: whitened f0 (per-utterance z-score)
  features[:, 0] = (f0 - f0_mean) / f0_std

  # Feature 1: log f0 of the RAW (non-whitened) values
  features[:, 1] = np.log(f0 + 1e-8)

  Feature 0 is speaker-normalized (whitened). Feature 1 is unnormalized
  raw log-F0 which retains absolute pitch level (encodes speaker identity).
  This partially defeats whitening: the model can still infer speaker from
  feature 1 even after whitening feature 0.

Fix:
  # Use whitened f0 for the log-f0 feature:
  f0_whitened = features[:, 0]  # Already computed
  features[:, 1] = np.log(np.abs(f0_whitened) + 1e-8)
  # Or log of re-scaled f0 using mean only (preserve shape, not level):
  features[:, 1] = np.log(f0 / (f0_mean + 1e-8) + 1e-8)

[M-06] O(N²) PYTHON LOOP FOR F0 INTERPOLATION — RUNTIME BOTTLENECK
File:    streamvc/f0_extractor.py — extract_f0()
Lines:   ~57–82

Problem:
  for i in range(len(f0_values)):
      if f0_values[i] == 0:
          left_idx = voiced_indices[voiced_indices < i]   # O(N) numpy
          right_idx = voiced_indices[voiced_indices > i]  # O(N) numpy
          ...

  For each unvoiced frame, this performs two O(N) numpy array indexing
  operations inside a Python for-loop. The total complexity is O(N²) per
  utterance. Since f0 extraction is called for every sample in every batch,
  this is the primary CPU bottleneck during training.

Fix:

  from scipy.interpolate import interp1d

  voiced_f0 = f0_values.copy()
  voiced_mask = voiced_f0 > 0
  if voiced_mask.sum() >= 2:
      x = np.where(voiced_mask)[0]
      y = voiced_f0[voiced_mask]
      interp = interp1d(x, y, kind='linear', bounds_error=False,
                        fill_value=(y[0], y[-1]))
      f0_interp = interp(np.arange(len(f0_values)))
  else:
      f0_interp = np.full_like(f0_values, 150.0)

[M-07] DISCRIMINATOR GROUPNORM BREAKS WITH SMALL CHANNEL COUNTS
File:    streamvc/discriminator.py — DiscriminatorBlock.__init__()
Line:    ~33

Problem:
  self.norm = nn.GroupNorm(min(32, out_channels // 4), out_channels)

  ScaleDiscriminator builds channels = [1, 64, 128, 256, 512] for 4 layers.
  The first channel `in_channels=1` never goes through GroupNorm, so that's
  fine. But if the architecture is modified to smaller hidden_dim (e.g.,
  hidden_dim=16), out_channels=16 → groups=min(32,4)=4 which might cause
  issues if out_channels is not divisible by the chosen groups for odd
  configurations.

  More critically: channels[0] = 1, channels[1] = hidden_dim. The FIRST
  DiscriminatorBlock takes in_channels=1 and out_channels=hidden_dim=64.
  GroupNorm(min(32,16), 64) → GroupNorm(16, 64) — valid.
  But if output channels ever become odd (non-multiple of groups), this
  silently produces wrong normalization or crashes.

Fix:
  # Use a more robust group selection:
  def safe_groupnorm(num_channels):
      for g in [32, 16, 8, 4, 2, 1]:
          if num_channels % g == 0:
              return nn.GroupNorm(g, num_channels)
  self.norm = safe_groupnorm(out_channels)

[M-08] TTS synthesize_batch IS NOT BATCHED — MISLEADING API
File:    tts/text_to_speech.py — synthesize_batch()
Lines:   ~120–145

Problem:
  def synthesize_batch(self, texts: list[str], ...):
      for text in texts:
          audio = self.synthesize(text, ...)  # Sequential, not batched!
          audios.append(audio)

  The method iterates sequentially with no GPU batching at all. The name
  implies batch synthesis (GPU-parallel), but it's a plain Python loop.
  If called with N texts, there are N separate model.generate_speech() calls,
  N vocoder passes, and N CPU↔GPU transfers. For the full pipeline, this
  is the TTS throughput bottleneck.

Fix:
  # SpeechT5 generate_speech supports batch inputs:
  def synthesize_batch(self, texts, speaker=None, speaker_embedding=None):
      inputs = self.processor(
          text=texts, return_tensors="pt", padding=True
      ).to(self.device)
      spectrograms = self.model.generate_speech(
          inputs["input_ids"],
          speaker_embedding.expand(len(texts), -1)
      )
      # Note: SpeechT5 generate_speech returns one spectrogram per input;
      # batch vocoding may require additional handling per HuggingFace docs.

[CF-01] CONTENT ENCODER PREDICTS HuBERT CENTROIDS FROM OWN FEATURES — CIRCULAR SUPERVISION
File:    streamvc/train.py — compute_hubert_targets() + train_step()
Status:  Conceptual mismatch with StreamVC paper

Problem:
  The StreamVC paper supervises the content encoder using ACTUAL HuBERT
  discrete units extracted from a pre-trained HuBERT model (offline).
  The k-means centroids (100 clusters) are learned from real HuBERT features.

  The implementation uses a learned LINEAR PROJECTION (content_projection)
  to map content encoder features (dim=64) to HuBERT space (dim=768), then
  assigns pseudo-labels by nearest centroid in THAT projected space.

  This is circular: the content encoder is trained to predict labels derived
  from its own projected outputs. The projection has no ground truth — it is
  trained simultaneously with the encoder. The centroids from HuBERT are used
  as targets, but the distance is computed in a learned (not fixed HuBERT)
  space. This collapses to trivially assigning all frames to the same cluster
  (the one nearest the mean of random projections).

Correct Design:
  Run a pre-trained HuBERT model on source audio OFFLINE (or at batch time)
  to extract actual speech unit frame labels. Store them or compute on-the-fly
  using the frozen HuBERT model. Remove content_projection entirely.

  In dataset.py or train_step():
    with torch.no_grad():
        hubert_outputs = frozen_hubert_model(source_audio)  # Real HuBERT
        hubert_features = hubert_outputs.last_hidden_state  # (B, T, 768)
        # Assign to centroids:
        distances = torch.cdist(hubert_features, self.hubert_centroids)
        hubert_targets = torch.argmin(distances, dim=-1)  # (B, T)
  Then supervise content_encoder's output_proj (num_classes=100) with
  cross-entropy against these frozen labels.

[CF-02] STOP GRADIENT APPLIED INCORRECTLY — DISABLES CONTENT SUPERVISION
File:    streamvc/model.py — StreamVC.forward()
Lines:   ~395–405

Problem:
  content_logits, content_features = self.content_encoder(source_audio)
  content_features_stopped = content_features.detach()   # Stop gradient
  # ...
  output_audio = self.decoder(content_features_stopped, ...)
  return output_audio, content_logits

  The stop gradient (detach) on content_features is intended to prevent
  the decoder from affecting the content encoder's representation learning.
  This is CORRECT per the paper.

  HOWEVER: content_logits is returned and used in train_step() for
  cross-entropy loss. The gradient DOES flow back to content_encoder
  through content_logits — this part is also correct.

  The issue: content_features.detach() means the decoder gradients
  can't reach content_encoder. But content_logits = output_proj(features),
  meaning output_proj IS trained. The features themselves ARE trained
  (via content_logits path). So the architecture intent is preserved.

  The REAL concept flaw: the decoder trains only on the DETACHED features,
  meaning if content features change significantly during training, the
  decoder sees a distribution shift it cannot backprop to fix. This creates
  a training instability known as "representation mismatch during adaptation."

Mitigation:
  Use an exponential moving average (EMA) of content features, or use the
  stop-gradient only after a warmup period where the content encoder is
  more stable. Alternatively, use a small teacher-student gap update rather
  than hard stop-gradient.

[CF-03] VOICE CONVERSION REQUIRES SPEAKER-PAIR SUPERVISION — DATASET LACKS IT
File:    streamvc/dataset.py
Status:  Training objective cannot be verified

Problem:
  The model is trained to reconstruct target_audio given source content.
  But because target is randomly selected (possibly same file), the model
  never receives a ground-truth supervising pair: there is no known-correct
  "converted" output for supervision.

  This is a self-supervised / reconstruction objective, which is valid IF:
  (a) source and target are different speakers (ensures voice conversion is needed)
  (b) The model receives the source content + target speaker, and the loss is
      measured against target (forcing matching target voice).

  Condition (a) is violated (same-speaker pairs allowed — see M-01).
  The training effectively becomes autoencoder reconstruction for same-speaker
  pairs and voice-cloning for different-speaker pairs, with no way to
  distinguish which objective is being optimized at each step.

Correct Design:
  Enforce different speaker pairs (see M-01 fix). Additionally, provide the
  model with speaker identity labels during training so losses can be weighted
  based on whether the pair is genuinely cross-speaker.

[CF-04] F0 EXTRACTED FROM SOURCE THEN FED TO DECODER AS-IS — NO SPEAKER NORMALIZATION
File:    streamvc/train.py — train_step()
Lines:   ~170–185

Problem:
  f0_features = self.f0_extractor(source_audio)  # Source speaker's f0!
  # ...
  output_audio = self.decoder(content_features, speaker_embedding, f0_features)

  The decoder uses the f0 extracted from the SOURCE speaker's audio. For
  voice conversion, the output should have the TARGET speaker's f0 contour
  (or at least a pitch-shifted version). Feeding raw source f0 into the
  target-conditioned decoder means the converted voice will retain the
  source speaker's exact pitch contour, defeating pitch-cloning.

  The whitening (per-utterance z-score) in f0_extractor partially addresses
  this by normalizing absolute pitch level, but relative contour shape
  (which still encodes speaker characteristics like pitch range) is preserved.

  Per the paper, f0 should be:
  1. Extracted from source (captures content prosody).
  2. Whitened to remove speaker-specific mean/variance.
  3. The target speaker's F0 statistics should be used to re-scale at inference.

  At TRAINING time, f0 whitening gives utterance-level normalization, but
  there is no "re-scaling to target speaker" step implemented anywhere.

Fix:
  At inference: extract target speaker f0 statistics from reference audio,
  then re-scale whitened source f0 to match target speaker's pitch range:
    f0_denormalized = f0_whitened * target_f0_std + target_f0_mean

SECTION 5 — PERFORMANCE RISKS

[P-01] CPU BOTTLENECK: F0 EXTRACTION IS SYNCHRONOUS ON CPU DURING TRAINING
File:    streamvc/f0_extractor.py, streamvc/train.py

Problem:
  F0ExtractorModule.forward() calls cpu().numpy(), runs parselmouth (Praat
  via ctypes), then moves result back to GPU. This CPU-bound operation
  runs synchronously IN the training loop, blocking GPU computation.
  For batch_size=16 with 2-second segments: 16 × parselmouth calls × O(N²)
  interpolation ≈ significant CPU stall per step.

Fix:
  Option A (recommended): Pre-extract and cache f0 features to disk during
    dataset preprocessing (as numpy arrays). Load cached f0 in __getitem__.
    This moves the CPU cost entirely out of the training loop.

  Option B: Use Python multiprocessing (DataLoader num_workers > 0) to
    parallelize f0 extraction across CPU cores while GPU trains.

  Option C: Replace parselmouth with a differentiable F0 estimator
    (e.g., CREPE, PENN) that runs on GPU.

[P-02] MEMORY LEAK RISK: RESAMPLER CREATED ON EVERY load_audio() CALL
File:    streamvc/audio_utils.py — load_audio()
Lines:   ~65–80

Problem:
  if sr != sample_rate:
      resampler = T.Resample(sr, sample_rate)
      audio = resampler(audio)

  A new T.Resample transform is instantiated on every load_audio() call
  when resampling is needed. For LibriTTS (all 16kHz) this is no-op, but
  if mixed-rate datasets are used, this creates thousands of small objects
  per epoch, pressuring the garbage collector.

Fix:
  Cache resampler by input sr using functools.lru_cache:
    from functools import lru_cache
    @lru_cache(maxsize=32)
    def _get_resampler(self, orig_sr, target_sr):
        return T.Resample(orig_sr, target_sr)

[P-03] CHECKPOINT CLEANUP DOES NOT HANDLE EPOCH CHECKPOINTS
File:    streamvc/train.py — save_checkpoint()
Lines:   ~365–375

Problem:
  checkpoints = sorted(self.checkpoint_dir.glob("checkpoint_step_*.pt"))
  if len(checkpoints) > self.config['checkpointing']['keep_last_n']:
      for old_ckpt in checkpoints[:-keep_last_n]:
          old_ckpt.unlink()

  The cleanup only considers checkpoint_step_*.pt files. The training loop
  ALSO saves checkpoint_epoch_N.pt files per epoch:
    self.save_checkpoint(name=f"checkpoint_epoch_{epoch}.pt")

  Epoch checkpoints are NEVER cleaned up, accumulating indefinitely.
  With 100 epochs, 100 files × ~model_size are retained, quickly
  filling disk (each .pt file is likely 20–80MB depending on model size).

Fix:
  Add a parallel cleanup for epoch checkpoints:
  epoch_ckpts = sorted(self.checkpoint_dir.glob("checkpoint_epoch_*.pt"),
                       key=lambda p: int(p.stem.split('_')[-1]))
  for old in epoch_ckpts[:-keep_last_n]:
      old.unlink()

[P-04] ALL 4 PIPELINE MODELS LOADED ONTO SAME DEVICE — VRAM EXHAUSTION
File:    run_pipeline.py — VoiceClonePipeline.__init__()

Problem:
  ASR (Distil-Whisper ~100M params), MT (NLLB-200 600M params), TTS (SpeechT5
  ~90M params + HiFiGAN), StreamVC (custom GAN). All are loaded to self.device
  which defaults to "cuda". In fp16/float16, these collectively require:
    ~50MB + ~1.2GB + ~180MB + ~100MB ≈ 1.6GB minimum
  Plus activations for a single inference batch. On a 4GB GPU, this is
  borderline. On a 6GB GPU, it leaves little room for safe operation.
  The pipeline never explicitly manages inter-model memory.

Fix:
  Offload models not currently in use to CPU between pipeline stages:
    self.asr_model.to('cpu'); torch.cuda.empty_cache()
    self.mt_model.to('cuda')
    # ... translate ...
    self.mt_model.to('cpu'); torch.cuda.empty_cache()
    self.tts_model.to('cuda')
  Or use accelerate's device_map="auto" for automatic offloading.

[R-01] SPLIT train.py — TRAINER CLASS IS DOING TOO MUCH
  StreamVCTrainer combines: model construction, data loading, loss

[R-02] UNIFIED AUDIO LOADING UTILITY
  audio loading is duplicated across 4 files using different backends:
    - dataset.py: librosa.load()
    - audio_utils.py: torchaudio.load()
    - run_pipeline.py: librosa.load()
    - test_streamvc.py: librosa.load()
  Standardize on one backend (torchaudio recommended for training
  as it supports GPU-accelerated transforms and avoids CPU bottleneck).


[R-03] CONFIG VALIDATION AT STARTUP
  The trainer accesses deeply nested config keys without validation:
    self.config['training']['discriminator']['scales']
    self.config['training']['gradient']['clip_norm']
    self.config['data']['num_workers']
  A missing or mistyped key raises a raw KeyError with no diagnostic context.
  Recommend using pydantic or dacite for config schema validation at startup.


[R-04] REMOVE sys.argv PROCESSING FROM __main__ BLOCKS
  Multiple files (tts, asr, mt) have argparse __main__ blocks for standalone
  testing. These are good, but they should import from a properly installed
  package rather than requiring execution from specific directories. The
  test scripts (test_tts.py, test_streamvc.py) partially duplicate this
  functionality. Consolidate into a unified test/eval harness.


[R-05] MAGIC NUMBERS SHOULD BE CONFIG-DRIVEN
  Multiple files hardcode values that should be in config:
    - f0_extractor.py: 150.0 (default f0 for unvoiced) — what basis?

    - audio_utils.py: 1e-8 (mel log floor), 1e-5 (STFT log floor)
    - model.py: dilation=2**i for content encoder, 2**(i%4) for decoder
  Move these to configs or named constants with explanatory comments.


[R-06] TYPE HINTS USE PYTHON 3.10+ SYNTAX IN CODE TARGETING 3.9+
